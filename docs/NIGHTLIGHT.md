# The night light

Blue out of the screen, on a schedule, across the whole phone. Why it needs
native code, why there are two ways of doing it, and which one you get.

---

## What it does

The screen's colour temperature follows a curve through the day: neutral in the
morning, warming so slowly you never catch it happening, fully warm by bedtime.
Like f.lux, and for the same reason — blue light late in the evening suppresses
melatonin, and the point of a wind-down is undermined by staring into daylight
right before it.

There are two shapes to choose from:

* **All day** (the default) warms continuously from the moment you get up. The
  ramp is raised to a power, so the first half of the day is imperceptible and
  most of the change still lands in the evening where it matters. A straight
  line makes mid-afternoon visibly orange, which is not what anyone wants.
* **Evening only** holds neutral all day and drops over the transition window
  before bed. This is what f.lux does by default.

Either way the day temperature is 6500K, which is neutral, so "on" during the
day applies **nothing at all** — the filter is genuinely invisible rather than a
permanent faint tint. That is what makes it something you can leave switched on
all year.

## Why this is native code

Because it has to work when NiFo is not running.

A web page can only tint itself. A night light that warms one app while the
browser, YouTube and the home screen stay blue is not a night light, and one
that only works while you happen to have NiFo open is worse. So the whole
feature lives in a Capacitor plugin under `native/nightlight/`, and the schedule
lives in Java with it.

That last part is the important design decision. The web layer writes the
configuration and reads the status back; it never computes a colour. If the
schedule ran in JavaScript, the filter would stop the moment the WebView was
torn down, which is most of the time.

### How the plugin ships

`android/` is regenerated by `npx cap add android` on every build and is not in
the repository, so anything patched into it after generation is thrown away.
`tools/patch-signing.mjs` gets away with that trick for four lines of Gradle;
for a service, a receiver, four classes and a manifest it would mean writing
Java inside JavaScript strings.

So the plugin is a real npm package in `native/nightlight/`, pulled in by a
`file:` dependency in `package.json`. Capacitor finds it like any other plugin,
adds it to `capacitor.settings.gradle` as a Gradle module, and merges its
manifest into the app's. Nothing has to be patched, the Java stays in `.java`
files, and `cap add android` can regenerate as often as it likes.

## The two filters

Which one runs is decided every minute, and the settings screen says which one
you are getting.

### The system filter, when it can

Android has its own Night Light, and it is a genuine colour transform applied in
the display pipeline. It covers everything, including the lock screen and the
permission dialogs an overlay is deliberately kept away from, and — the part
that actually matters — it **multiplies**, so it takes blue out of white without
touching black.

Driving it needs `WRITE_SECURE_SETTINGS`, which is signature-level and cannot be
requested at runtime. It can only be granted over adb, once, ever:

```
adb shell pm grant gr.nifo.app android.permission.WRITE_SECURE_SETTINGS
```

Nothing needs switching on afterwards. The service checks for the permission on
every tick, so the next minute simply takes the better road. Its one limitation
is range: the hardware filter typically bottoms out near 2600K, where the
overlay will go to 1900K.

### The overlay, when it cannot

A full-screen window with `TYPE_APPLICATION_OVERLAY`, `FLAG_NOT_TOUCHABLE` so
every touch falls straight through, and `FLAG_LAYOUT_NO_LIMITS` so it covers the
status and navigation bars rather than leaving two untinted strips across a warm
screen. It needs the "Display over other apps" permission, which has a settings
screen but no runtime dialog.

**It washes rather than multiplies, and that is not fixable.** Every window on
Android is composited source-over, so the most an overlay can do is

```
out = amber·a + screen·(1−a)
```

which takes blue out of bright pixels correctly and lifts black pixels *towards*
amber, which is the wrong direction. There is no flag that changes this;
blending happens in SurfaceFlinger, below anything an app can reach. The alpha
is capped at 0.55 in `Curve.java` so the lift stays tolerable, and the settings
screen says so outright instead of pretending the two paths are equivalent.

This is also why the browser fallback is, oddly, the better model: CSS *can*
multiply, so `mix-blend-mode: multiply` on a page overlay does the correct
thing. It just cannot reach past NiFo's own screens.

## The colour maths

`Curve.java` is pure: given a config and a minute of the day it returns a
colour, which is what lets the settings screen plot the whole day by asking for
one sample every fifteen minutes.

**Kelvin to RGB** is the usual black-body approximation. **Interpolation happens
in mireds**, a million over Kelvin, not in Kelvin itself. Kelvin is perceptually
lopsided: 6500K to 5500K is barely visible and 3000K to 2000K is enormous, so a
ramp linear in Kelvin does almost nothing for most of its length and then lurches
at the end. Mireds are close enough to perceptually even that a linear ramp looks
like a steady change, which is the entire illusion the feature depends on.

**The overlay colour is normalised against the day temperature**, so at the day
temperature the multipliers are exactly 1, the alpha is 0 and there is literally
nothing drawn. Alpha comes from the blue channel, because blue is what this
exists to remove and is always the most attenuated of the three.

## Battery, and staying alive

A foreground service, because Android will not keep a background one, which
means a permanent notification. It is `IMPORTANCE_MIN`, so it sits silently at
the bottom of the shade, and it carries the one control anybody ever wants:
**pause for an hour**. It also says which of the two filters is running and what
temperature the screen is at.

The service recomputes once a minute and stops ticking entirely on
`ACTION_SCREEN_OFF`, because nothing is visible while the screen is off. That is
the difference between a filter you forget about and one that shows up in the
battery screen. A `BootReceiver` puts it back after a restart, without which a
phone that rebooted overnight would have the filter off for exactly the hours it
was meant to cover.

## Where it stands down

The progress gallery and the monthly check-in's camera. Judging a photo through
an amber wash is misleading and comparing two of them is worse, so the router
suspends the filter on both and lifts it on the way out.

That suspend is a plain flag rather than a timed pause, because it is not a user
decision. It is cleared at every app launch, so a crash mid-gallery cannot leave
the filter off indefinitely.

## Testing it without a phone

`Curve.java` has no Android dependencies beyond `SharedPreferences`, so it can be
compiled and run on a desktop JVM to check the schedule and the colours
numerically — the curve is monotonic through the day, the day temperature is a
literal no-op, midnight-wrapping shifts work, mireds interpolate evenly. That is
worth knowing, because the rest of the plugin cannot be tested anywhere but on a
device.

The browser fallback covers the rest: `npm run dev` gives you the settings
screen, the live preview strip and a working filter over NiFo's own pages.

## What is deliberately not here

* **Sunrise and sunset from your location.** Fixed hours instead, defaulting to
  the times the prayer rule already uses, with a button to match them. A
  location permission for something two time fields answer is a poor trade.
* **Dimming.** Strength weakens the tint rather than darkening the screen;
  brightness is the brightness slider's job.
* **A tile in the app.** This is a setting, not a practice. It has no streak and
  nothing to track, so it lives under Settings and not on Today.
